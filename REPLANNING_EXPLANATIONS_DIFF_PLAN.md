# План реализации объяснений перепланирования на основе diff

## 1. Цель

Реализовать понятное диспетчеру объяснение перепланирования рабочего дня.

Объяснение строится из двух источников:

1. события, из-за которого было запущено перепланирование;
2. различий между предыдущим и новым планом.

Система не пытается объяснить внутреннюю работу оптимизатора. Она объясняет наблюдаемый бизнес-результат: что произошло и что изменилось.

## 2. Архитектурное решение

Слой объяснений должен быть независим от способа построения плана. Исходный и новый планы могут быть получены при помощи:

- Timefold;
- другого VRP-оптимизатора;
- LLM или агентной системы;
- ручного редактирования диспетчером.

Для слоя объяснений все эти способы должны предоставлять один и тот же нейтральный снимок плана.

Целевой поток:

```text
Событие перепланирования
        │
        ▼
Предыдущий PlanSnapshot + новый PlanSnapshot
        │
        ▼
PlanDiffDomainService
        │
        ▼
PlanDiff
        │
        ▼
Обработчик конкретного типа события
        │
        ▼
ReplanningExplanation
```

## 3. Границы функциональности

### 3.1. Входит в первую версию

- фиксация причины запуска перепланирования;
- сравнение двух версий плана;
- обнаружение изменений исполнителя, порядка и планового времени;
- обнаружение перехода заявки из неназначенного состояния в назначенное и обратно;
- три вида обоснования: аварийная заявка, отмена заявки, сход исполнителя;
- краткое резюме и список конкретных изменений для UI.

### 3.2. Не входит в первую версию

- объяснение первоначального плана, для которого нет предыдущей версии;
- доказательство глобальной оптимальности плана;
- объяснение внутренних score, штрафов и весов оптимизатора;
- доказательство того, что другой исполнитель или маршрут был хуже;
- полная диагностика причин неназначения, если они не переданы извне;
- генерация естественного текста с помощью LLM.

## 4. Текущая основа в проекте

В проекте уже есть часть необходимой модели:

- `Schedule.previousSchedule` может связывать версии плана;
- `Schedule.slots` содержит заявки и плановые времена;
- `ReplanEventDto` уже различает `URGENT_REQUEST`, `CANCEL_REQUEST` и `ENGINEER_UNAVAILABLE`;
- `RequestActionAudit` фиксирует ряд операций с назначениями.

Эти классы не следует использовать как готовый diff без доработки:

- `previousSchedule` пока не используется в процессе перепланирования;
- исполнитель слота сейчас определяется через изменяемое `Request.assignedCrew`;
- в `ScheduleSlot` нет явной позиции заявки в маршруте;
- аудит не хранит изменения порядка и планового времени;
- тип события и его параметры не привязаны к новой версии плана.

`RequestActionAudit` может остаться аудитом действий, но не должен быть единственным источником diff.

## 5. Обязательные инварианты

### 5.1. Неизменяемые версии плана

Предыдущий план нельзя изменять при создании нового. Иначе diff будет сравнивать новый план с частично перезаписанной версией его самого.

### 5.2. Исполнитель хранится в снимке

В каждом слоте версии плана нужно хранить исполнителя. Поле `Request.assignedCrew` описывает текущее состояние заявки и не является историческим снимком.

### 5.3. Неназначенные заявки относятся к конкретной версии

Набор неназначенных заявок нужно фиксировать для каждой версии. Его нельзя восстанавливать позже из текущего `Request.assignedCrew`, потому что назначения могли уже измениться.

### 5.4. Событие хранится явно

Тип события, время и идентификатор затронутой заявки или бригады должны быть связаны с новой версией плана. Причину нельзя восстанавливать только по набору изменений.

### 5.5. Diff содержит факты, а не текст

Доменный diff не должен хранить фразы вроде «маршрут был оптимизирован». Он должен хранить типизированные изменения и значения «до»/«после». Текст формируется на следующем слое.

## 6. Нейтральный снимок плана

Рекомендуемая логическая модель:

```text
PlanSnapshot
  planId
  previousPlanId
  targetDate
  regionId
  routes[]
    crewId
    crewName
    visits[]
      requestId
      position
      previousRequestId
      arrivalTime
      startTime
      endTime
  unassignedRequestIds[]
```

`PlanSnapshot` не должен иметь зависимостей от Timefold. Адаптер из `Schedule` или из результа любого планировщика должен построить этот снимок до вызова diff-сервиса.

На первом этапе модель можно реализовать Java-record'ами без JPA-аннотаций. Это позволит изолированно реализовать и протестировать diff.

## 7. Контекст перепланирования

Тип триггера объявляется внутри контекста:

```text
ReplanContext.TriggerType
  EMERGENCY_REQUEST_CREATED
  REQUEST_CANCELLED
  CREW_BECAME_UNAVAILABLE
```

Контекст:

```text
ReplanContext
  triggerType
  occurredAt
  triggerSubjectId      // идентификатор заявки или бригады в зависимости от triggerType
  previousPlanId
  newPlanId
```

Единый `triggerSubjectId` не допускает невалидную комбинацию двух взаимоисключающих nullable-полей. Для событий заявки он содержит идентификатор заявки, для `CREW_BECAME_UNAVAILABLE` — идентификатор бригады.

## 8. Модель diff

```text
PlanDiff
  previousPlanId
  newPlanId
  requestChanges[]
  crewRouteChanges[]
  summary
```

Типы изменений заявок:

```text
RequestChange.Type
  ADDED_TO_PLAN
  ADDED_AS_UNASSIGNED
  REMOVED_FROM_PLAN
  ASSIGNED_FROM_UNASSIGNED
  BECAME_UNASSIGNED
  REASSIGNED
  ORDER_CHANGED
  PLANNED_TIME_CHANGED
```

Изменение должно хранить необходимые значения:

```text
RequestChange
  requestId
  types[]
  previousCrewId
  newCrewId
  previousPosition
  newPosition
  previousPredecessorRequestId
  newPredecessorRequestId
  previousStartTime
  newStartTime
  startTimeDeltaMinutes
```

Общие изменения маршрута:

```text
CrewRouteChange
  crewId
  previousRequestCount
  newRequestCount
  addedRequestIds[]
  removedRequestIds[]
  reorderedRequestIds[]
  shiftedRequestIds[]
```

`PlanDiff` не должен содержать ссылки на JPA-entity. Для связи используются идентификаторы и неизменяемые значения.

## 9. Алгоритм сравнения

### 9.1. Индексация

Из каждого `PlanSnapshot` строится карта:

```text
requestId -> RequestPlacement
```

`RequestPlacement` содержит исполнителя, позицию, предыдущую заявку и плановые времена. Неназначенная заявка также должна иметь placement, но без `crewId`, позиции и времени.

### 9.2. Порядок классификации

Для каждой заявки:

1. Если заявки не было в предыдущем снимке, но она есть в новом и назначена, фиксируется `ADDED_TO_PLAN`.
2. Если заявки не было в предыдущем снимке, но в новом она осталась без исполнителя, фиксируется `ADDED_AS_UNASSIGNED`.
3. Если заявка была неназначена, а стала назначена, фиксируется `ASSIGNED_FROM_UNASSIGNED`.
4. Если назначенная заявка стала неназначенной, фиксируется `BECAME_UNASSIGNED`.
5. Если изменился `crewId`, фиксируется `REASSIGNED`.
6. Если исполнитель не изменился, но изменилась предыдущая заявка, фиксируется `ORDER_CHANGED`.
7. Если изменилось плановое начало работы, фиксируется `PLANNED_TIME_CHANGED`.
8. Если заявка исчезла из нового снимка и это соответствует событию отмены, фиксируется `REMOVED_FROM_PLAN`.

Одна заявка может иметь несколько изменений. Например, переназначение может сопровождаться изменением времени.

### 9.3. Как не создавать шумный diff

Нельзя определять перестановку только по изменению числового индекса. При вставке одной аварийной заявки индекс изменится у всех последующих заявок, хотя их относительный порядок не изменился.

Для фиксации `ORDER_CHANGED` в первой версии следует сравнивать `previousRequestId`. Позиции нужны для UI и деталей, но не должны быть единственным признаком перестановки.

## 10. Объяснения для трёх use case

Объяснение должно состоять из:

- типа и заголовка;
- краткого резюме;
- структурированного списка изменений;
- счётчиков переназначений, перестановок, сдвигов времени и неназначенных заявок.

### 10.1. Появление аварийной заявки

Основной текст:

> План перестроен после появления аварийной заявки №{requestId}.

Варианты деталей:

- «Аварийная заявка назначена бригаде “{crewName}” на {startTime}»;
- «Для аварийной заявки №{id} не найден исполнитель; она осталась неназначенной»;
- «Заявка №{id} переназначена с бригады “{oldCrew}” на бригаду “{newCrew}”»;
- «Начало заявки №{id} сдвинуто с {oldTime} на {newTime}»;
- «Заявка №{id} после пересчёта осталась без исполнителя».

Нельзя утверждать, что конкретная заявка была вытеснена аварийной из-за приоритета, если diff показывает только одновременное изменение.

### 10.2. Отмена заявки

Основной текст:

> План перестроен после отмены заявки №{requestId}.

Варианты деталей:

- «Отменённая заявка удалена из маршрута бригады “{crewName}”»;
- «Заявка №{id}, ранее остававшаяся без исполнителя, добавлена в маршрут бригады “{crewName}”»;
- «Последующие работы бригады “{crewName}” начнутся раньше»;
- «Другие назначения и порядок заявок не изменились».

Фраза «освободилось время» допустима как описание удаления слота. Фраза «поэтому выбрана другая заявка» недопустима без дополнительного основания.

### 10.3. Сход исполнителя с маршрута

Основной текст:

> План перестроен, потому что бригада «{crewName}» стала недоступна.

Варианты деталей:

- «{count} будущих заявок снято с маршрута недоступной бригады»;
- «Заявка №{id} переназначена бригаде “{newCrew}”»;
- «Заявка №{id} осталась без исполнителя»;
- «Выполненные заявки и заявка в работе не изменились».

В этом use case детальный список должен в первую очередь показывать судьбу заявок сошедшей бригады, а затем прочие изменения.

## 11. Формат результа объяснения

```text
ReplanningExplanation
  type
  title
  summary
  occurredAt
  triggerSubjectId
  counters
    assigned
    unassigned
    reassigned
    reordered
    timeChanged
  changes[]
    requestId
    changeTypes[]
    message
    previousCrewId
    newCrewId
    previousStartTime
    newStartTime
```

Пример API-фрагмента:

```json
{
  "type": "EMERGENCY_REQUEST_CREATED",
  "title": "План перестроен из-за аварийной заявки",
  "summary": "Аварийная заявка №98816 назначена бригаде «Соколов». Изменены 3 плановые работы.",
  "occurredAt": "14:00:00",
  "triggerSubjectId": 98816,
  "counters": {
    "assigned": 1,
    "unassigned": 0,
    "reassigned": 1,
    "reordered": 1,
    "timeChanged": 2
  },
  "changes": [
    {
      "requestId": 98816,
      "changeTypes": ["ADDED_TO_PLAN"],
      "message": "Аварийная заявка добавлена в маршрут бригады «Соколов» на 14:20",
      "previousCrewId": null,
      "newCrewId": 1,
      "previousStartTime": null,
      "newStartTime": "14:20:00"
    }
  ]
}
```

В API нужно возвращать как коды и значения «до»/«после», так и готовую фразу. Коды нужны UI для цвета, иконки и фильтрации; текст должен формироваться на backend, чтобы бизнес-формулировки не дублировались в Vue.

## 12. Разделение ответственности

Рекомендуемое размещение логики в текущей архитектуре:

```text
domain/dto/replanning
  PlanSnapshot
  PlanDiff
  RequestChange
  CrewRouteChange
  ReplanContext
  ReplanningExplanation

domain/service/replanning
  PlanDiffDomainService
    RequestPlacement (private)
  ReplanningExplanationDomainService

application/schedule
  use case, который загружает версии, строит snapshot,
  вызывает diff и возвращает API DTO
```

Доменные сервисы не должны:

- читать из репозиториев;
- зависеть от REST DTO;
- зависеть от Timefold-классов;
- изменять `Schedule`, `Request` или `EngineerCrew`.

Набор типов триггера закрыт и не планируется к расширению, поэтому `ReplanningExplanationDomainService` использует исчерпывающие `switch` по `ReplanContext.TriggerType`. Отдельная policy-иерархия для трёх фиксированных сценариев не требуется.

## 13. Хранение версий

Для полного цикла перепланирования нужны как минимум:

- отдельный `Schedule` для каждой версии;
- ссылка на предыдущую версию;
- статус, позволяющий отличить действующий план от предложенного и заменённого;
- исполнитель в `ScheduleSlot`;
- порядковый номер или `previousRequestId` в `ScheduleSlot`;
- контекст события перепланирования.
- набор неназначенных заявок для каждой версии или эквивалентный неизменяемый снимок.

Рекомендуемые статусы:

```text
CALCULATING
PROPOSED
ACTIVE
SUPERSEDED
REJECTED
```

Конкретную JPA-модель и схему миграции нужно согласовать с разработчиком процесса перепланирования. Diff-слой не должен самостоятельно менять жизненный цикл `Schedule`.

## 14. Этапы реализации

### Этап 1. Чистая модель snapshot и diff

Реализовать без Spring, JPA, Timefold и REST:

- `PlanSnapshot`;
- внутренний `RequestPlacement` в `PlanDiffDomainService`;
- `PlanDiff`;
- `RequestChange`;
- `CrewRouteChange`;
- `PlanDiffDomainService`;
- unit-тесты.

Это первый рекомендуемый инкремент. Он не требует готового процесса перепланирования и может разрабатываться изолированно.

### Этап 2. Контекст события и три политики объяснения

- добавить `ReplanContext`;
- реализовать обработчик аварийной заявки;
- реализовать обработчик отмены;
- реализовать обработчик схода бригады;
- проверить формулировки snapshot-тестами.

### Этап 3. Адаптер текущей модели расписания

- построить `PlanSnapshot` из версии `Schedule`;
- проверить стабильный порядок слотов;
- не допускать чтение исторического исполнителя из `Request.assignedCrew`;
- связать новую версию с предыдущей и событием.

### Этап 4. API

- добавить DTO объяснения;
- возвращать его вместе с предложенным планом или отдельным endpoint;
- оставить доменные коды независимыми от внешнего JSON-формата.

### Этап 5. UI

- показать причину перепланирования;
- показать счётчики изменений;
- подсветить новые, удалённые и переназначенные заявки;
- показать старое и новое время;
- дать диспетчеру возможность показать только изменённые маршруты.

## 15. Тестовые сценарии

### 15.1. Diff-сервис

1. Два одинаковых snapshot дают пустой diff.
2. Новая заявка в маршруте даёт `ADDED_TO_PLAN`.
3. Новая заявка без исполнителя даёт `ADDED_AS_UNASSIGNED`.
4. Неназначенная заявка, получившая бригаду, даёт `ASSIGNED_FROM_UNASSIGNED`.
4. Изменение бригады даёт `REASSIGNED` с корректными значениями «до»/«после».
5. Изменение `previousRequestId` даёт `ORDER_CHANGED`.
6. Простое увеличение индекса из-за вставки перед заявкой не помечает весь остаток маршрута как полную перестановку.
7. Изменение времени хранит знаковую разницу в минутах.
8. Переназначение и сдвиг времени могут сосуществовать для одной заявки.

### 15.2. Объяснения

1. Каждый `ReplanContext.TriggerType` выбирает свои заголовок, резюме и приоритет изменений.
2. Аварийное объяснение упоминает trigger-заявку.
3. Объяснение отмены отделяет отменённую заявку от заявок, ставших неназначенными.
4. Объяснение схода сначала показывает заявки сошедшей бригады.
5. Пустой diff сохраняет причину перепланирования и явно сообщает об отсутствии изменений.
6. Сообщение заявки перечисляет все её типы изменений, а не только первый.
7. Тексты не содержат утверждений об оптимальности, штрафах или внутренних решениях планировщика.

## 16. Критерии готовности

Функциональность готова, когда:

1. Каждая новая версия плана имеет неизменяемую предыдущую версию.
2. Событие перепланирования явно связано с новым планом.
3. Diff одинаково работает для планов из любого источника.
4. Для каждой затронутой заявки доступны коды изменений и значения «до»/«после».
5. Для каждого из трёх use case формируется отдельное краткое обоснование.
6. Объяснение не зависит от Timefold, score или классов конкретного планировщика.
7. Одинаковые snapshot дают объяснение без изменений.
8. UI может подсветить изменённые назначения, порядок и время без повторного вычисления diff.

## 17. Риски и решения, которые нужно согласовать

### 17.1. Что считать изменением времени

Нужно выбрать:

- фиксировать любое изменение с точностью до минуты; или
- ввести порог, например 5 минут, чтобы не показывать незначительные сдвиги.

Для первой версии рекомендуется точное сравнение, а фильтрацию мелких сдвигов выполнять на уровне представления.

### 17.2. Как отличать отменённую заявку от неназначенной

Отменённая заявка не должна попадать в счётчик неназначенных. Для этого diff должен получать `ReplanContext` или статус заявки.

### 17.3. Какую версию показывать диспетчеру

Нужно явно разделить:

- действующий план;
- новый предложенный план;
- уже подтверждённую новую версию.

Diff для подтверждения должен сравнивать действующий план с конкретным предложенным планом, а не с «последним найденным» планом.

## 18. Первый следующий шаг

Начать с чистой доменной реализации `PlanSnapshot` и `PlanDiffDomainService`.

На этом шаге не нужно:

- изменять `Schedule` и `ScheduleSlot`;
